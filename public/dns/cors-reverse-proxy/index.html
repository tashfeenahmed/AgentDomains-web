CORS Behind a Reverse Proxy Explained

Configure `Access-Control-Allow-Origin` and `OPTIONS` preflight handling cleanly when your API sits behind an edge reverse proxy.

1. Engineering Breakdown

Browsers evaluate Cross-Origin Resource Sharing (CORS) against the public URL in the address bar (`https://myapp.makes.fyi`), not your upstream origin hostname. Ensure your backend responds to `OPTIONS` preflight requests with 204 and echoes your allowed frontend origin.

Common Pitfalls

  • When sending cookies (`credentials: "include"`), you cannot use `Access-Control-Allow-Origin: *` — return the explicit frontend origin.

Reverse Proxy vs URL Forwarding

          
Reverse proxy (`set_proxy`) serves your origin directly under your domain with edge HTTPS; URL forwarding (`set_forward`) issues an HTTP 301/302 redirect to another URL.

        
        
          Edge Routing
          
301 vs 302 HTTP Redirects

          
302 is temporary and safe to change anytime (AgentDomains default); 301 is permanent and aggressively cached by browsers and search engines.
